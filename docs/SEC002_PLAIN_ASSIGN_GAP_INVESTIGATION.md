# EPIC-SEC-002: Plain Field Assignment Gap — Investigation Report

> Status: **Confirmed gap, but NOT a source of missed vulnerabilities in the 6 audited repos.**  
> Date: 2026-07-29

---

## 1. The Full IR Call Chain

### Step 1 — `syn::Stmt` → `StatementKind`

In `cfg/builder.rs`, the `RawFunctionVisitor` converts `syn` statements:

```
syn::Stmt::Expr(syn::Expr::Assign(...), semicolon=Some)
  → StatementKind::Semi(ExpressionNode { kind: ExpressionKind::Assign { left, right } })
```

A plain reassignment like `group.admin = admin;` in a function body is parsed as `syn::Stmt::Expr` with a trailing semicolon, producing `StatementKind::Semi` wrapping an `ExpressionKind::Assign`.

### Step 2 — `StatementKind` → `IRInstruction`

In `ir_converter.rs`, `convert_statement_node_to_ir`:

```rust
StatementKind::Expr(expr) | StatementKind::Semi(expr) => {
    ir_instructions.push(IRInstruction::Expr(convert_expr_node_to_ir(expr)));
}
```

`convert_expr_node_to_ir` for `ExpressionKind::Assign` produces:

```rust
ExpressionKind::Assign { left, right } => IRExpression::Assign {
    left: Box::new(convert_expr_node_to_ir(left)),
    right: Box::new(convert_expr_node_to_ir(right)),
}
```

So the final IR for `group.admin = admin;` is:

```
IRInstruction::Expr(
    IRExpression::Assign {
        left:  FieldAccess { object: Variable("group"), field: "admin" },
        right: Variable("admin"),
    }
)
```

### Step 3 — `get_mutable_write_expression_ir` in SEC-002

```rust
fn get_mutable_write_expression_ir(&self, instr: &IRInstruction) -> Option<IRExpression> {
    match instr {
        IRInstruction::Assignment(assign) => self
            .get_expr_write_target_ir(&assign.value)
            .or(Some(IRExpression::Variable(assign.target.clone()))),
        IRInstruction::Expr(expr) => self.get_expr_write_target_ir(expr),
        _ => None,
    }
}

fn get_expr_write_target_ir(&self, expr: &IRExpression) -> Option<IRExpression> {
    match expr {
        IRExpression::Call { target, method, .. } => {
            if let Some(m) = method {
                if m == "borrow_mut" || m == "try_borrow_mut" || m == "try_borrow_mut_data" {
                    return Some(*target.clone());
                }
            }
            None
        }
        _ => None,   // ← IRExpression::Assign falls here → returns None
    }
}
```

**The gap is confirmed:** `get_expr_write_target_ir` only handles `IRExpression::Call` with specific borrow methods. An `IRExpression::Assign` falls into the `_ => None` arm and is silently ignored.

## 2. What Does Each Variant Actually Cover?

| IR Pattern | Generated by | Handled by SEC-002? |
|---|---|---|
| `IRInstruction::Assignment` | `let x = some_account.borrow_mut()` | ✅ Yes — falls to `get_expr_write_target_ir` via `.value` field |
| `IRInstruction::Expr(IRExpression::Call { method: "borrow_mut" })` | `some_account.borrow_mut()` standalone | ✅ Yes |
| `IRInstruction::Expr(IRExpression::Assign { ... })` | `account.field = value;` plain assignment | ❌ **No — completely missed** |

## 3. Real-World Prevalence in the 6 Audited Repos

Searched for privileged plain-assignment patterns (`.(authority|owner|admin|signer|initializer)\s*=[^=]`) in actual instruction source files:

### squads-v4
- **0 instances** of plain privileged field assignment in instruction bodies.
- `ctx.accounts.transaction.executed_index = ...` exists but `executed_index` is not an authority-like name.

### marginfi
- **0 instances** in `programs/marginfi/src/instructions/` proper.
- Occurrences are in `self.authority = authority` inside struct initialization helpers, not live instruction handlers being audited.

### mango-v4
- **3 candidate instances** in instruction files:
  1. `account.fixed.owner = owner;` — [`account_create.rs:37`](file:///Users/aksh/epic-audit-sweep/mango-v4/programs/mango-v4/src/instructions/account_create.rs)
  2. `group.admin = admin;` — [`group_edit.rs:29`](file:///Users/aksh/epic-audit-sweep/mango-v4/programs/mango-v4/src/instructions/group_edit.rs)
  3. `group.admin = ctx.accounts.creator.key()` — [`group_create.rs:15`](file:///Users/aksh/epic-audit-sweep/mango-v4/programs/mango-v4/src/instructions/group_create.rs)

### Analysis of Mango-v4 Instances

**`account_create.rs`** — `account.fixed.owner = owner;`:
- `AccountCreate` struct has `pub owner: Signer<'info>`. The `owner` field **is a `Signer<>`** at the Anchor level → SEC-002 would not flag it regardless, because Anchor itself enforces signing for `Signer<>` fields.
- The function receives `owner: Pubkey` as an argument (not the accounts struct); this is initialization code — expected pattern for a new account.
- **EPIC already correctly produces no SEC-002 warning here** (the write target `account` is not an account struct field with an authority-sounding name in the instruction handler's symbol table).

**`group_edit.rs`** — `group.admin = admin;`:
- `GroupEdit` accounts struct: `pub admin: Signer<'info>`, plus `has_one = admin` constraint. **Both** Anchor-level signer and key equality are enforced declaratively.
- EPIC currently emits no SEC-002 warning for this function. With the fix applied, it still shouldn't — the `admin` field in the accounts struct **IS a declared `Signer<>`**, so `GuardFact::Signer` is injected via `extract_guards_from_accounts_struct`, and `has_dominating_signer_check` would return true.
- **No missed vulnerability.**

**`group_create.rs`** — `group.admin = ctx.accounts.creator.key()`:
- Initialization of a new group — safe by design, similar to `account_create`.
- **No missed vulnerability.**

## 4. Verdict

| Question | Answer |
|---|---|
| Is `IRExpression::Assign` a confirmed gap in `get_mutable_write_expression_ir`? | **Yes, definitively confirmed.** |
| Does this cause SEC-002 to silently miss any real vulnerability in the 6 audited repos? | **No** — all instances of the pattern use accounts that are either (a) declared `Signer<>` in the Anchor struct, (b) initialization code for newly-created accounts, or (c) not in instructions where an authority-like account name exists without a signer guard. |
| Could this gap cause missed vulnerabilities in other programs not yet audited? | **Yes** — a future program with `admin: UncheckedAccount<'info>` (not `Signer<>`), where the only authority enforcement is a manual inline check (`require!(ctx.accounts.admin.key() == stored_admin)`), writing to a privileged field via plain assignment, would NOT be flagged by SEC-002. |

## 5. High-Level Fix (Not Implemented)

The fix is a one-line addition to `get_expr_write_target_ir` in `epic_sec_002.rs`:

```rust
fn get_expr_write_target_ir(&self, expr: &IRExpression) -> Option<IRExpression> {
    match expr {
        IRExpression::Call { target, method, .. } => {
            if let Some(m) = method {
                if m == "borrow_mut" || m == "try_borrow_mut" || m == "try_borrow_mut_data" {
                    return Some(*target.clone());
                }
            }
            None
        }
        // ADD THIS ARM:
        IRExpression::Assign { left, .. } => Some(*left.clone()),
        _ => None,
    }
}
```

This returns the left-hand side of any assignment expression as the write target, allowing the resolver to trace it back to an account symbol and check for dominating signer guards.

**Risk of adding this:** Could generate new SEC-002 false positives for structs that use plain assignment during initialization (e.g., `group_create.rs`). These would need to be filtered by checking whether the assignment happens inside an `#[account(init)]`-tagged context or is a pure initialization function. The false-positive risk is low but non-zero.

---

## 6. Recommendation

**Pre-demo:** Document as a known limitation — "SEC-002 detects writes via `borrow_mut()` chains; plain struct-field reassignments are not currently detected as write triggers." The gap does not affect the accuracy of the demo repos.

**Post-demo / Beta 2:** Implement the one-line fix to `get_expr_write_target_ir`. Regression-test it against all 6 audited repos to validate no net increase in false positives. Add a new unit test with a synthetic program that uses plain field reassignment as the only write to a `UncheckedAccount`-typed authority.
